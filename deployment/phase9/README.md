# Phase 9 — AWS infrastructure and deployment runbook

This is an **undeployed** configuration. Phase 9 does not authorize `terraform apply`, AWS resource creation, migrations against a live database, or a deployment. Commands below that change infrastructure/hosts are for a later, explicitly authorized deployment. Use this guide instead of the historical `deployment/AWS_EC2_DEPLOYMENT.md` (local MySQL/PM2/HTTP instructions do not describe this architecture).

## Architecture and repository assumptions

Terraform lives in `infra/terraform`. Singapore (`ap-southeast-1`) hosts VPC `10.0.0.0/16`, EC2/Nginx/API/worker, private RDS, S3, Lambda, SQS and operational SNS. Billing alarm/SNS and account-wide monthly Budget use the `us-east-1` provider. Nothing introduces NAT Gateway, ALB, ECS, API Gateway, Redis or DynamoDB.

The public `10.0.1.0/24` subnet in AZ A routes through an Internet Gateway. EC2 uses one Elastic IP, only inbound 80/443, outbound HTTPS to AWS/package services, and outbound 3306 to the DB SG. No key pair, port 22, public API port, or SSH deployment exists. Use Session Manager with an IAM Identity Center operator session; require current SSM Agent (at least 3.3.40.0) with `ssmmessages`. DNS uses the VPC resolver and time sync uses Amazon Time Sync. S3 uses a free gateway endpoint on the EC2 route table; the endpoint does not replace public access to SSM/Logs/Parameter Store.

DB subnets `10.0.10.0/24` (AZ A) and `10.0.11.0/24` (AZ B) have an explicitly associated route table with no default internet route. A **two-AZ DB subnet group is an RDS placement requirement, not Multi-AZ replication**. The DB instance has `multi_az=false` and runs only in AZ A. EC2 and RDS are single points of failure; expect downtime during failure, replacement and maintenance. No HA claim is made.

`docs/SPEC.md` still describes an old static frontend. The current user worktree already has `backend/` and React/Vite `frontend/`; this phase preserves both and serves its built `frontend/dist` directly from Nginx. No framework migration is performed. Historical Phase 6B/7 runtime gates remain open; this IaC work does not waive them or certify the application for production.

## Local preparation (no AWS writes)

1. Use Terraform >=1.10,<2 with the pinned AWS provider 5.100.x. This version is deliberately bounded; upgrades require a reviewed lockfile/schema check. Copy `terraform.tfvars.example` to ignored `terraform.tfvars`. Replace the AMI, domain, unique bucket, account/OIDC ARN, repository, email and engine version. Verify AMI owner/architecture, RDS version availability and support lifecycle in Singapore before a future plan. Examples are not deployable defaults.
2. Build the validator ZIP on a clean Linux build runner: run `npm ci` at repository root using the existing lockfile; create a fresh staging directory; copy `lambdas/s3-file-validator/{index.js,validator.js}` to its root, add `package.json` containing `{"type":"module"}`, and copy the installed root `node_modules` into it. ZIP the *contents*, not the enclosing directory. Test with Node 22. This conservative bundle includes extra dependencies but pins the SDK to the repository lock; never rely on an unpinned runtime SDK or ZIP `.env`/application data. Ensure compressed ZIP <50 MB and uncompressed <250 MB. Record ZIP SHA-256 with the release and set `lambda_zip` to that file. A smaller dependency bundle can be reviewed in Phase 10A. Do not run the app during packaging.
3. Run from `infra/terraform`:

   ```sh
   terraform fmt -check -recursive
   terraform init -backend=false
   terraform validate
   ```

   Init downloads providers only; it does not create AWS infrastructure. Keep `.terraform.lock.hcl` in version control. `filebase64sha256` requires the real ZIP for plan. Tests may use an inert local ZIP solely for offline validation; never deploy it.
4. Run `python deployment/phase9/test_launch.py` and `python infra/tests/check_infra.py` from repository root. The latter needs `python-hcl2` installed in an isolated tools environment. Neither reads `.env` nor accesses AWS. Static checks do not prove live IAM/network behavior.

State is operationally sensitive even without passwords. No backend is auto-created here. Before any later plan/apply, configure a separately bootstrapped private, encrypted, versioned S3 state bucket and native S3 locking (`use_lockfile=true`, Terraform >=1.10). See `backend.hcl.example`; use a reviewed `backend "s3" {}` declaration then `terraform init -backend-config=backend.hcl`. No DynamoDB is needed. Scope operator state access to that key and `.tflock`; require MFA/SSO and restrict state readers. Do not commit state/plan/tfvars. Do not use the application data bucket for state, import secret values into state, or fetch a SecureString/Secrets Manager value with a Terraform data source. Offline init here uses local backend and creates no state resources.

## Secret bootstrap, identities and database

RDS uses `manage_master_user_password=true`: AWS generates and stores the master password in Secrets Manager; Terraform holds only the secret ARN, not the password. This limited RDS-managed secret is necessary to create RDS without plaintext Terraform credentials. Runtime application credentials belong in Parameter Store, not in that master secret. EC2/Lambda/CI cannot retrieve the master secret. KMS for runtime SecureString has rotation, a 30-day deletion window and Terraform destruction protection.

After infrastructure creation is separately authorized:

1. An audited bootstrap operator, using short-lived credentials, reads the RDS-managed secret into memory via SDK on a trusted workstation. Permit `secretsmanager:GetSecretValue` only for that ARN. Use Session Manager's remote-host port-forward document through the EC2 instance to the private RDS endpoint; restrict operator `ssm:StartSession` to that instance/document. Do not add a network ingress rule. Use an SDK/database script with certificate validation; retain the real RDS hostname for TLS verification even if forwarding locally. Never paste secrets into shell commands, CLI `--password`, Terraform variables, terminal output, shell history, recorded sessions or files on disk.
2. Download the official [Singapore RDS CA bundle](https://truststore.pki.rds.amazonaws.com/ap-southeast-1/ap-southeast-1-bundle.pem), verify its provenance/expiry, and install as `/etc/cloud-files/rds-ca.pem` mode 0644 owned by root. The backend's optional `DB_SSL_CA` enables mysql2 certificate verification; the launcher always sets it for this deployment. Missing/invalid CA fails startup. Create an application DB user with a cryptographically generated password and `REQUIRE SSL`, restricted to the EC2 private subnet host pattern, with only SELECT/INSERT/UPDATE/DELETE on `cloud_file_manager.*`. Do not run the application as the master user.
3. Create a separate temporary migration user (also REQUIRE SSL), with the schema DDL and DML grants needed by the checked-in migrations. Stop API/worker before migrations; follow `docs/MIGRATIONS.md`, rehearse on a disposable database, take a snapshot and execute `backend/scripts/migrate.js up` with migration credentials only in the child environment. Verify `status` and revoke the temporary migration account afterward. Never grant runtime DDL or automatically migrate in a service startup.
4. In that same trusted bootstrap program, write a single JSON **SecureString** parameter named `/<name>/runtime` with KMS key `parameter_key_arn`. Use `boto3`/AWS SDK `PutParameter(Value=...)` with an in-memory object, not Terraform or command-line values. Allow the bootstrap identity only this parameter's PutParameter and the key's Encrypt/GenerateDataKey through SSM. Standard tier suffices when JSON is <=4 KiB. The runtime JSON keys, all strings, are:

   | Key | Value source |
   | --- | --- |
   | DB_HOST | Terraform `db_host`, real RDS endpoint |
   | DB_NAME | `cloud_file_manager` |
   | DB_USER | Dedicated runtime user |
   | DB_PASSWORD | Generated runtime password, never an example/default |
   | AWS_S3_BUCKET | Terraform `bucket` |
   | APP_ORIGIN | Exact `https://<domain>` |
   | DB_PORT | Optional `3306` |

   Optional tuning keys are explicitly allowlisted in `launch.py` and documented in `.env.example`. Keep orphan cleanup report-only. No static AWS key, NODE_OPTIONS, PATH, TLS bypass or executable path is accepted from the parameter. Missing/invalid/non-SecureString config, AccessDenied, or a timeout prevents startup; there is no cached plaintext or mock fallback.
5. Rotate the runtime password with a MySQL dual-password overlap where supported: set new password retaining old, update Parameter Store, restart API and worker, verify TLS/DB access, then discard old password. Roll back while the old password still works if bootstrap fails. The launcher fetches once per process start, not on every request. Processes necessarily hold DB credentials in memory/environment; trusted host root can inspect them. Disable core dumps and never inspect/log `/proc/*/environ` or AWS responses. No `.env` should be installed in the release.

IAM intentionally shares the EC2 instance role between API/worker on this one host. It signs writes only to incoming, copies only to objects, reads exact incoming/object versions and current reports, and deletes/list-versions only for objects. It cannot write validator reports. Lambda reads only exact incoming versions, writes only reports, sends only to its failure queue, and cannot read DB/Parameter Store. Wildcard resources occur only where SSM channel APIs and log-group discovery lack resource-level authorization. The S3 bucket denies HTTP and public access but has **no mandatory SourceVpce condition**: authenticated presigned browser POST/GET and the outside-VPC Lambda work from public AWS endpoints. CORS is restricted to the domain and exposes version headers.

CI uses an existing GitHub OIDC provider with exact `aud` and `repo:owner/repo:environment:production` claims. Require GitHub protected environment reviewers and branch restrictions. The role can only update code/read configuration of this validator, no PassRole, IAM, secrets, S3 data, remote commands, infrastructure apply or EC2 login. Updating Lambda code is trusted report-writing authority; treat release review accordingly. Phase 10A may add a separately reviewed EC2 deployment workflow; this phase creates no pipeline or broad administrator CI role. Keep the ZIP/hash synchronized with Terraform after a CI release to avoid rollback on a future apply.

## Host installation, DNS and HTTPS

All steps here are a later operator deployment over Session Manager. Use a reviewed AL2023 x86_64 AMI with recent SSM Agent, install Node 22, Python 3, AWS CLI v2, Nginx, Certbot and CloudWatch Agent from verified official sources. Verify actual binary paths match `/usr/bin/node`, `/usr/bin/python3`, `/usr/local/bin/aws`; adapt reviewed units if the distro differs. HTTPS-only package repositories are required by egress rules. Keep chrony/SSM enabled. No software or credentials are fetched via user data.

1. Build the frontend (`npm ci`, `npm run build`) on a Linux runner, run approved tests, and stage a reviewed release at `/opt/cloud-files/releases/<release-id>`. Install production backend dependencies from the lockfile; retain the backend's ESM package.json, sources, migration scripts and `frontend/dist`. Validate Linux-compatible dependencies. Transfer a checksummed artifact over an approved authenticated HTTPS channel. Do not put deployment artifacts under the S3 `incoming/` event prefix. Create a root-owned `current` symlink to the release. Use a non-login `cloud-files` OS user; release/launcher/unit files are root-owned and not writable by that user. Nginx needs read/execute access to the frontend path.
2. Install `launch.py` at `/opt/cloud-files/launch.py`, the CA bundle as above, and create `/var/log/cloud-files` root-owned mode 0750. Install the service template under `/etc/systemd/system/cloud-files@.service`, replacing NAME. Install the logrotate rule. Systemd writes root-owned logs before dropping privileges; the application cannot modify its supervisor or release. The worker's default 25s drain is below `TimeoutStopSec=40`; do not increase `WORKER_SHUTDOWN_MS` past that without updating the unit. Logrotate copytruncate has a small loss window; Phase 10A can improve transport.
3. Point a DNS **A** record for the domain to Terraform `public_ip`. No AAAA record is configured because this VPC is IPv4-only. Confirm propagation; review restrictive CAA records. DNS is managed by the existing registrar/provider, not an assumed Route53 zone. No wildcard certificate is needed.
4. Initially install only the port-80 server block from `nginx.conf.example` (the 443 block refers to certificates that do not exist yet). Replace DOMAIN, remove distro default sites, create `/var/www/acme`, run `nginx -t`, and start Nginx. Obtain a certificate with `certbot certonly --webroot -w /var/www/acme -d <domain> --email <operator-email> --agree-tos`. Port 80 serves only challenges and HTTPS redirects. After issuance install both blocks and run `nginx -t` before reload. Use Let's Encrypt staging for rehearsals to avoid issuance limits.
5. Enable the distro Certbot renewal timer (or install a twice-daily systemd timer invoking `certbot renew --quiet --deploy-hook 'nginx -t && systemctl reload nginx'`). Execute `certbot renew --dry-run`; verify timer scheduling and certificate expiry alerting before launch. Certificate private keys remain root-only on encrypted EBS and never enter Terraform/state/repository. Renewals use HTTP-01; do not close port 80 while using this method.
6. After migrations and Parameter Store bootstrap, run `systemctl daemon-reload` then `systemctl enable --now cloud-files@server cloud-files@worker`. Verify `ss -lntp` shows **127.0.0.1:3000**, not 0.0.0.0; public 3000/3306/22 must fail. Test `https://<domain>/api/health`, SPA deep links, secure session cookie/CSRF, direct S3 upload exposing `x-amz-version-id`, report/finalize and version-pinned download. Nginx serves frontend directly because the current backend static-path resolution is not used by this deployment.
7. Install the agent JSON with NAME substituted and start CloudWatch Agent using its `amazon-cloudwatch-agent-ctl -a fetch-config -m ec2 -c file:<path> -s` command. Terraform precreates log groups/retention; agent IAM intentionally cannot create groups or change retention. Configure Session Manager preferences to stream to `/<name>/ssm` using encrypted transport, verify log delivery, and avoid entering secrets in sessions. Do not stream Nginx error logs until confirming they cannot contain query-bearing URLs. Confirm both SNS email subscriptions manually. The failure queue retains events 14 days; investigate/replay only after verifying exact bucket/key/version and the existing idempotency contract. SQS is not the application job queue.

## Retention, cost assumptions and alerts

RDS storage is encrypted, automated backups retain seven days, final snapshot is required, deletion protection is on, and Terraform `prevent_destroy` covers RDS/S3/KMS/EC2/failure queue. EC2 root EBS is encrypted and retained on termination. This is a safety barrier, not a backup plan: `prevent_destroy` cannot protect a resource removed from configuration or deletion outside Terraform. Restrict IAM deletion authority. Snapshot restoration and application-consistent S3/DB recovery must be rehearsed later.

S3 versioning is enabled. Lifecycle expires current and noncurrent **incoming/** and **processing-results/** objects after 30 days by default; noncurrent clocks start when a version becomes noncurrent, so total lifetime may exceed 30 days. Retained delete markers are harmless but require reviewed eventual cleanup. No rule expires any `objects/` version or marker: only the ownership-aware durable purge/reconciliation workflow can remove those. Resolve stalled uploads/DEAD jobs well before the recovery window; for longer incidents extend/disable temporary expiry before it runs. It is not possible to recover a source version after lifecycle has permanently deleted it.

Costs assume 730 hours/month, one t3.small EC2 (20 GiB gp3), one public IPv4/EIP, one db.t4g.micro RDS (20 GiB gp3, autoscaling ceiling 100 GiB), seven-day backups, small S3 dataset plus retained versions, one KMS key, one RDS-managed Secrets Manager secret, low-volume Lambda/SQS/SNS, and 30-day CloudWatch log retention. CPU burst credits, snapshots over allowance, outbound internet downloads, requests, versions, logs and abandoned retained EBS can materially increase cost. The **USD 75 budget is an example alert threshold, not an estimated price or spending cap**. Before authorization, price actual Singapore SKUs and workload in the [AWS Pricing Calculator](https://calculator.aws/) and record the estimate/date; no Free Tier eligibility is assumed. No NAT/ALB hourly cost is introduced. S3 gateway endpoint itself has no hourly charge.

Enable “Receive CloudWatch billing alerts” in the billing account first. [AWS billing metrics are in us-east-1](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/monitor_estimated_charges_with_cloudwatch.html); the alarm uses that region and USD EstimatedCharges. The Budget is account-wide (including unrelated workloads) and alerts at 80%; billing alarm threshold is the full example amount. In Organizations use the payer's supported billing context and verify permissions/metrics, not just resource creation. Budgets/metrics have delays and **do not stop spending**. Confirm SNS email subscriptions and test delivery. Missing billing metrics remain “insufficient data”, not a healthy zero-cost signal.

## Acceptance and next-phase gates

Before any deployment: reviewed real artifact, provider lock, AMI and engine version, state backend/locking, account/OIDC trust and cost estimate; later authorization for plan/apply is separate. After deployment authorization: verify SSM access without SSH, routing/SG denial, database TLS and least-privilege account, backups, S3 public/TLS/versioning/IAM denials, browser presigning from outside VPC, Lambda duplicate/error/failure-destination paths, DNS/TLS renewal, log delivery/retention and SNS/billing activation. Confirm actual Lambda concurrency quota supports reserved concurrency 5. Missing Lambda/SSM/CloudWatch quota or IAM provisioning permission is an operator gate, not a reason to broaden runtime roles.

Phase 10A should build monitoring/CI atop these reviewed interfaces. Phase 6B/7 real MySQL concurrency, migrations, worker-kill/recovery and S3 versioned purge tests plus current frontend browser acceptance remain required; no static Terraform check substitutes for them.

## Teardown checklist — never a blind destroy

- Obtain explicit data-owner authorization; freeze uploads, stop API/worker and wait for in-flight writes/leases. Export DB metadata and inventory every S3 version/delete marker; resolve jobs and compare references.
- Take a uniquely named manual RDS snapshot; rehearse restore and record endpoint/KMS requirements. Keep versioned S3 data, KMS key, backups and logs for the approved retention period. Inventory EBS volumes/snapshots and certificates. No `force_destroy` or `aws s3 rm --recursive` shortcut.
- Prefer removing stateless compute only while retaining data resources in a dedicated managed state. Review state moves/imports under a lock. Retained log groups (`skip_destroy=true`) need import if reused. Deleting resource blocks bypasses `prevent_destroy`, so review the entire plan.
- Only after retention and approval, deliberately change source `prevent_destroy` and AWS deletion protection in a reviewed change. RDS final snapshot identifier must be unique (the default fixed name must be changed if already used); leave `skip_final_snapshot=false` and `delete_automated_backups=false`. Cancel teardown on snapshot failure.
- Do not empty a bucket until exact-version inventory/export verification and explicit permanent-deletion approval. Drain/archive the SQS failure queue before removing its guard. Revoke parameters/roles/OIDC repository trust only after services are stopped; an account-shared OIDC provider is not owned by this module.
- Remove DNS, revoke unused certificates, release EIP, inspect retained root EBS and snapshots for ongoing cost. Schedule KMS deletion only after all dependent retained material is intentionally retired; its 30-day window is a final recovery opportunity. Keep billing alerts until residual charges settle and archive state securely.

# Phase 10A — observability and delivery

Implementation only; no AWS deployment, live migration, notification or recovery was executed.
Express/Sequelize/MySQL and the existing React/Vite frontend remain unchanged architecturally.

## Logging and correlation

API and worker emit one JSON object per line. The server generates a UUID `request_id` (untrusted incoming IDs are never accepted), returns `X-Request-Id`, and carries it through async service calls. Migration 007 adds nullable `jobs.request_id`; a model default records the originating request in the same job transaction. `job_queued` is emitted only after commit. Claims/retries retain `job_id` and the original request ID across restarts. Scheduled/legacy jobs without an originating HTTP request have null request IDs. Worker logs include both IDs; their audits retain their existing ownership rules.

Lambda runs independently of the API and does not receive the HTTP request. Its AWS invocation request ID and deterministic `report_id` connect validation logs to the worker's report log; the report schema is unchanged. Do not invent an HTTP request ID for S3 events.

The logger redacts nested cookies, authorization, credentials, passwords, secrets, tokens, presigned URLs, headers, payload/body/SQL and all Error objects. SDK exception text/SQL bind values are not logged. Request logs omit paths, query strings, request/response bodies and headers; Nginx uses escaped JSON without URI/query/cookie fields. Never pass arbitrary user text as an event name. CloudWatch Logs Insights: filter on `request_id`, then `job_id`, then `report_id`; these identifiers are log fields, **never metric dimensions**. Access to logs still requires least privilege and 30-day retention.

## Health and metrics

- `/health/live`: process HTTP loop responds, no dependency checks.
- `/health/ready`: DB authentication probe; 503 on failure, shutdown or two-second timeout. Concurrent callers share one in-flight probe so a hung DB does not fill the pool. No DB/credential details are exposed. `/api/health` remains a legacy liveness endpoint; deployment must use `/health/ready`.
- Worker samples every 30 seconds after a successful DB backlog query. `heartbeat=1` also requires recent polling/lease-renewal progress. Failed/hung queries produce no healthy sample. Shutdown cancels sampling and discards late results. A heartbeat proves worker/DB responsiveness, not completion of every S3 operation; oldest-work/backlog/dead-job alarms cover that distinction.
- Backlog counts due QUEUED jobs (future seven-day purge/expiry schedules are excluded). Oldest work includes due queued age and RUNNING age. Dead count includes all DEAD jobs and remains nonzero until operator resolution.
- CloudWatch log metric filters use `CloudFiles/<deployment-name>` without dimensions. Host agent uses `CloudFiles/Host`, aggregates RAM and root disk to `InstanceId`, and drops original metrics. AWS metrics use only fixed instance/DB/function/queue identities.

Terraform supplies a dashboard plus alarms for API readiness/5xx/latency, worker heartbeat, backlog/age/dead jobs, EC2 status/CPU, RAM/disk, RDS CPU/free storage/free memory, Lambda errors/throttles/destination failures, failure queue depth/age, and existing budget/billing alerts. Thresholds are starting values: API errors >5/5 min, mean latency >2 s, backlog >100, oldest >600 s, RAM/disk/CPU >85%, DB storage <2 GiB, free memory <128 MiB. Most require two five-minute periods; readiness requires three one-minute periods. Missing heartbeat/readiness/host metrics breach, while event-driven Lambda errors with no invocations do not. Tune only after measuring a reviewed workload. Backlog sampling scans jobs; monitor query cost as the retained table grows.

After separately authorized host setup, install root-owned `probe.py` and the probe service/timer; install the updated CloudWatch Agent example, replacing `NAME`. The probe calls loopback readiness every minute and appends JSON to the collected API log. Enable its timer and the agent; verify fresh metrics and JSON parsing before accepting alarms. A host-local probe does not prove DNS/TLS or public Nginx availability: CD performs external HTTPS smoke, and certificate checks belong to the runbook. The node instance role gets PutMetricData only for the host namespace.

SNS email endpoints come from `alert_email`. Confirm both regional operations and us-east-1 billing subscriptions, then perform an explicitly authorized test notification/alarm in the test environment; verify delivery and recovery notification. Terraform creation alone does not confirm email. Missing CloudWatch billing configuration is not zero cost. References: [CloudWatch Agent dimensions](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-Agent-Configuration-File-Details.html), [GitHub OIDC and protected environments](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws).

## CI

`.github/workflows/ci.yml` runs on push/PR/manual dispatch, with read-only repository permissions. It runs ESLint, npm audit (high/critical block), disposable MySQL 8.4 migrations twice, backend/frontend tests including opt-in MySQL concurrency tests, Python release/bootstrap tests, parsed-HCL security guardrails, Terraform fmt/init without backend/validate and frontend build. No AWS credentials are available to CI. Empty MySQL root password exists only in the disposable CI service, not application defaults or deployment configuration.

Tests no longer automatically load `.env`. CI sets `LOAD_DOTENV=false`; local integration requires explicit `MYSQL_TEST_ENABLED=true` and DB_* for a disposable database. Do not use production DB_* for tests. Local unit runs leave the flag unset.

CI prunes development dependencies and archives explicit application paths, production `node_modules`, frontend build, migration files, lockfile and `release.json`; it refuses .env content. Name and manifest carry full commit SHA, with SHA-256 sidecar. The artifact is Linux x86_64/Node 22; Windows build output is not a deployable substitute. GitHub retains it for 30 days; retain required rollback releases before expiry. Lambda publication remains the separately reviewed Phase 9 ZIP/publisher flow; this CD workflow activates API/worker/frontend artifacts and does not silently update Lambda.

## CD activation gates and bootstrap

CD has **only workflow_dispatch**, never a push trigger. Terraform `enable_cd=false` by default; workflow also refuses until protected production environment `CD_ENABLED=true`. Configure required reviewers and only the main deployment branch. Configure `DEPLOY_ROLE_ARN`, `RELEASE_BUCKET`, `INSTANCE_ID`, `RELEASE_DOCUMENT`, `PUBLIC_ORIGIN` from reviewed outputs. `github_deploy_subject` must exactly match the repository's production-environment OIDC subject (new repositories may use immutable IDs). No wildcard trust or long-lived AWS keys. The existing Phase 9 Lambda publisher is a separate role.

Opting in provisions a private encrypted versioned release bucket, an OIDC application role limited to its release prefix and one SSM document/EC2 instance, and an SSM command document limited to stage/migrate/deploy/rollback plus validated hex SHA/checksum arguments. No Terraform apply privilege. Use an SSM Agent supporting ENV_VAR interpolation (3.3.2746.0 or newer); older agents fail closed. Serialize workflow runs and host operations with concurrency plus flock.

Host bootstrap is manual and separately authorized:

1. Retain Phase 9 Nginx/systemd/launcher setup, Node 22 and AWS CLI. Install Python **3.12+** at `/usr/bin/python3.12` for the release controller/probe; it uses safe tar extraction APIs. Lambda remains Node 22.
2. Install reviewed `release.py` and `probe.py` under `/opt/cloud-files`, root-owned, not writable by `cloud-files`; never replace them from an application archive. `/opt/cloud-files/releases`, `current` and parent directory must also be root-owned. Preserve a known-good Phase 10A-compatible initial release in `releases/<SHA>` and point `current` to it before using CD; first-host bootstrap is not rollback.
3. Create root-owned mode-0600 `/etc/cloud-files/release.json` with non-secret fields `bucket`, `runtime_parameter` (`/NAME/runtime`) and `migration_parameter` (`/NAME/migration`). Provision migration SecureString outside Terraform with the launcher's approved keys and a DB identity with DDL rights; runtime identity retains ordinary application rights plus SELECT on schema_migrations. The shared EC2 role can retrieve both parameters when CD is enabled: this single-host architecture does **not** isolate migration secrets from a compromised runtime process. A future privilege-boundary redesign needs explicit scope approval.
4. Rehearse upgrades, verify a snapshot and review backward schema compatibility for the previous artifact before enabling CD. Install probe timer and Agent, confirm SNS, and check free disk space for both extracted releases and temporary archive. No automatic release deletion occurs.

Manual workflow inputs select a successful **CI** run on main, its exact full SHA, operation deploy/rollback, and an explicit migrate flag. Provenance verification rejects PR runs, failed runs, wrong workflow, mismatched SHA and rollback-with-migration. Downloaded bytes are checked before upload and again on the host; staging rejects path traversal, secrets, devices and escaping symlinks. Existing SHA directories are immutable.

Stage never changes `current`. Migration is a separate step, stopping both services, loading migration credentials only in the child process and leaving services stopped on failure. Deploy uses a read-only migration `check` gate, switches the symlink, starts API/worker, and tests readiness, frontend HTML and worker service and a fresh healthy worker sample after restart. Local smoke failure restores the previous application and returns failure even if rollback succeeds. External HTTPS smoke runs afterwards; if it fails, investigate DNS/TLS/Nginx and manually dispatch rollback if application regression is confirmed. External smoke failure does not automatically undo a successful local release. A disconnected runner/SSM timeout leaves state uncertain: inspect the command/host before retrying.

Automated rollback requires artifacts supporting the migration `check` command and structured heartbeat; a pre-10A artifact requires a separate manual rollback rehearsal. Rollback selects a retained successful CI artifact with `operation=rollback`, migrate=false. It uses the same checksum, staging, schema gate and smoke checks. Application rollback never reverses schema/data. Migration runner is forward-only; migration 007 is nullable/additive and compatible with the previous app. Incompatible future DDL/backfills require a separately reviewed restore/forward-fix plan and must not use automatic application rollback. A snapshot restore can lose post-snapshot writes and needs DB/S3 consistency review; it is not executed by this workflow.

GitHub Actions references currently use major version tags; pin reviewed action commit SHAs before enabling production if organization policy requires immutable third-party action references. Real GitHub/OIDC/SSM/systemd/Agent/SNS acceptance remains an environment gate, not an offline test result.
